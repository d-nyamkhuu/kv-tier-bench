    Methods & data

    How the estimate is made

    • Prefill time = vLLM's overhead (per request and per prompt token) + the model's FLOPs ÷ (the GPU's dense peak, BF16 or FP8 as the model was released, × its prefill share of peak × TP × TP efficiency). Matrix multiplies run at that share; attention at a fixed fraction of it. With a cached prefix, only the rest is computed, but its attention still covers the whole prompt. Each instance (one GPU, or a TP group) prefills one request at a time, first come first served; waiting counts toward TTFT.
    • Models: sizes and FLOPs are derived from each model's config.json and card. FLOPs: 2 × active parameters per token (MoE counts only the experts a token uses), plus attention: every earlier token in full layers, at most the window in sliding-window layers, the top-k tokens in sparse layers, and the indexer's scores over all tokens. KV per token counts the layers that keep every token; grouped-query heads are split over TP, and a latent (MLA) cache is copied on every TP rank, as vLLM does. Linear-attention state and the last window of sliding-window layers are a fixed part of every cached prefix, whatever its length. KV and state are bf16 unless the card gives another size. MoE prefill runs at the dense share of peak: assumption.
    • Models bigger than a node run across several nodes, as vLLM deploys them: tensor parallel inside a node, pipeline stages across nodes, each stage holding its share of the layers. Memory adds up over all the instance's GPUs (the weights are held once). A request passes the stages in turn, so its prefill takes as long as on one node holding everything, plus a hop per stage: the network's latency + the hidden states (hidden size × 2 bytes per token) ÷ its bandwidth. Each node loads and sends its own layers' KV, so cache loads and transfers get every node's links, and the instance's nodes pool their CPU memory and disks. The next request enters the first stage as soon as it is free (assumption: ideal pipelining).
    • Fixed-state models (linear or sliding-window attention) resume only where a state was saved: the end of an earlier stored sequence (a conversation's previous turn). A shared system prompt alone gives them no hit. A model without fixed state resumes at any cached block. assumption: vLLM keeps one state per cached sequence.
    • GPU figures come from NVIDIA datasheets. Prefill shares of peak come from InferenceX vLLM runs (H200 for Hopper, B200 for Blackwell); the RTX PRO 6000 has no published prefill result, so its share is fitted on s1. TP efficiency is from H200 and B200 runs, which use NVLink.
    • Decode runs on GPUs of its own (disaggregated) in batches of up to 1,024 sequences (vLLM's default max_num_seqs on GPUs with 70+ GiB), using requests ready at each step. The configured maximum, active KV memory and optional speed target limit each batch. Each step reads the weights and the batch's KV at 60% of peak memory bandwidth (Databricks), or is bound by its FLOPs when that takes longer. An MoE step reads the dense part (attention, shared experts, embeddings) and only the routed experts its tokens picked: with k of E experts per token, a batch of b touches 1 − (1 − k/E)b of them, assuming even routing (real routers are skewed, so they touch fewer). Expert counts and sizes come from each config.json. One Kimi K3 token reads 16 of 896 experts; a batch of 256 reads nearly all of them. Small-batch MoE decode is not checked against a measurement: no published single-request decode time for these models was found. Under TP, each step also adds a fixed all-reduce time per layer, fitted on InferenceX's TP runs of a dense model (it does not grow with the batch). It is applied as is to MoE models and to data-parallel attention (an assumption): at TP 8 it is 5–6 ms of each step, which is what keeps Kimi K3 below OpenRouter's speed. TTFT includes the KV transfer to the decode GPU and the first decode step. With a decode speed per request set, a new sequence joins a batch only if the estimated step still meets the target. A smaller batch means more decode GPUs and a higher output price. Below the speed even at batch 1, the request runs alone and the page says so. The OpenRouter button fills in the model's p50 throughput from OpenRouter's compare page.
    • Speculative decoding: a drafter proposes tokens and the model checks them all in one step, so a step yields several tokens. Checking costs FLOPs and expert reads for every drafted position, but the weights and KV are read once. The drafter costs its layers at the model's size: once for parallel drafters (DFlash, DSpark), once per token for autoregressive ones (MTP, EAGLE-3). So the speed-up is large for small batches and shrinks as the batch grows. Where checking drafts would slow a step down, the drafter is switched off; production drafters shrink their checking as load grows (DSpark). Accepted tokens per step are measured on 4–14B models at temperature 1 on MT-Bench (DSpark paper, Table 1: EAGLE-3 2.66, DFlash 3.11, DSpark 3.72). MTP's 1.875 is DeepSeek-V3's 85–90% acceptance of the second token. On large MoE models these are assumptions; set your own, or use Custom for drafters with no preset. MTP needs the checkpoint's own heads (Qwen3.8, GLM-5.3, MiniMax-M3). EAGLE-3, DFlash and DSpark need a draft model trained for the model; DeepSeek V4.1 Flash ships its DSpark drafter (its three next-token layers, block of 5), used with its own shape. Against measurements: at one request the model is 17% optimistic for DFlash. As the batch grows, measured speed-ups fall gradually from 4–8 requests on, while the model keeps the whole gain until the step turns compute-bound. So at moderate batches the drafter's gain here is an upper bound.
    • Expert parallelism (MoE decode): the routed experts spread over more GPUs than one TP instance. Each group of TP GPUs runs its own batch, and each GPU reads the dense part and only its own experts, so a step reads far fewer weights. Every MoE layer then sends each token to its experts and back: FP8 out, BF16 back, as DeepSeek serves. That goes over NVLink inside the NVLink domain (8 GPUs on HGX, 72 on GB200 NVL72) and over InfiniBand beyond it, at DeepEP's measured rates (39–98 GB/s per GPU by EP size). Two-batch overlap (off by default) hides that traffic behind compute; the measured runs sit between the model with and without it, nearer to without. Without stages, a model too big for one node decodes on the expert GPUs. Checked against Kimi K2.5 on GB200 with experts over 16 GPUs and DeepSeek-V3's production deployment over 144 GPUs. Without overlap the model is within about 20% at large batches and 27% too fast at 32 sequences per GPU (see the checks).
    • Serving precision: as released, or quantized as most providers serve. FP8: 1 byte per weight, FP8 compute (twice BF16's peak) and an FP8 KV cache. FP4: NVFP4 weights (4 bits plus an FP8 scale per 16 values, 4.5 bits), an FP8 KV cache, prefill at the FP8 rate (InferenceX's DeepSeek-R1 NVFP4 runs on B200 fit it, not the FP4 peak), and decode compute in FP4 on Blackwell (FP8 elsewhere). Weights never grow past what was released, linear-attention state stays bf16, and FP8 prefill reaches the same share of its faster peak as BF16 assumption. Quality loss from quantization is not modeled.
    • Attention across a TP group: data parallel by default (each GPU keeps whole KV for its own requests, as MLA models are served at scale with vLLM's --data-parallel-size and expert parallelism), or tensor parallel, vLLM's default, where a latent (MLA) cache is copied on every GPU. Prefill time is the same either way: assumption.
    • Cache loads: from CPU memory, a fixed latency + bytes ÷ the host link (54–56 GB/s on PCIe 5.0 through vLLM's offloading, py-kvcache). From a lower tier, the tier's latency + bytes ÷ its bandwidth, then the CPU → GPU copy. Bandwidth = the published peak × the share a KV load through vLLM reaches; each variant lists its sources. Values with no source are marked assumption.
    • Cache tiers use eager write-through for complete prompt chunks. CPU memory and bounded local SSDs check their 80% eviction watermark every second and remove 20% of entries in LRU order. Lookup starts with the instance’s GPU, then CPU, local disk, shared storage and peer CPU. Serving settings can give peers priority over shared storage. A hit ends at the first block no tier holds; the rest is recomputed. A cached prefix is always loaded, even when recomputing would be faster, as vLLM v0.34.0 does.
    • Software constants (vLLM's overhead per request and per token, attention's efficiency, the CPU-load latency) are not published anywhere; they are fitted on s1 and editable below.
    • GPUs in one node do not share KV caches. NVLink bandwidth is drawn in the diagram but does not enter the numbers. TP above 1 on PCIe-only GPUs (RTX PRO 6000, L40S) uses the NVLink TP efficiency: an assumption.
    • Peer nodes: a hit is a block in another node's CPU memory, pulled over the network. It needs 2+ nodes and CPU memory.
    • Cost: every GPU is paid for the whole time, busy or not. Prefill GPUs = nodes × GPUs per node; dedicated decode GPUs are sized to peak concurrent attention groups and rounded to whole instances. Pooled estimates charge measured GPU-seconds. Private disks bill provisioned capacity or estimated retained bytes separately on each node, according to the selected product. Object storage is billed on what is written per hour, kept for the retention time, plus any per-GB upload and retrieval fees (S3 Express); AWS presets also charge per PUT, GET and HEAD. CPU memory and the network are part of the VM. GPU prices are Nebius on-demand.
    • Cost at 60% busy: at a fixed cluster and load every GPU is paid for the whole time, so a faster tier cuts TTFT but barely the bill. What it buys is headroom: prefill takes less GPU time per request, so the same GPUs serve more requests. The page's "$ per 1,000 requests at 60% busy", the tier lab's sweep, the comparison across models and the tier-mix map (by default; it can show the cost at your load instead) raise or lower the request rate until the prefill GPUs are busy 60% of the time (a few proportional steps, the last few percent closed in proportion: prefill GPUs' $ per request scale with 1 / rate, decode and storage stay per request), then price a request there. The provider comparison loads its reference deployments the same way. TTFT is always at your load, except across models, where both setups get the traffic that keeps GPU + CPU memory alone 60% busy.
    • Cost per 1M tokens: the prefill GPUs' cost is split by what their busy time served. Computing uncached tokens (with their attention over the cached part) goes to input; loading cached blocks goes to cached input; the per-request overhead is shared by token count. Idle time is split the same way. Storage goes to cached input, decode GPUs to output. A cached price above the input price means caching costs more than it saves for that setup.
    • Large clusters (over 8 nodes) are replayed at 8 nodes with the same load per node, and totals scaled up. With round-robin and random routing, this approximates how often a conversation returns to a node. Disk reads and writes share bandwidth within each node. Object storage, peer traffic and KV handoff share the modeled network interface on the prefill node. A peer read also reserves the source interface. Object storage has no cluster-wide service quota in this model.
    • Synthetic conversations start at random (Poisson). Each follow-up waits for the previous reply to finish before its sampled think time starts. Uploaded traces keep their arrival timestamps. Each turn adds a message and its answer to the context. All conversations share one system prompt. The first minutes (warm-up) fill the caches and are left out.
