# Can LMCache run the simulator’s cache hierarchy?

The simulator now defaults to complete prompt chunks, eager write-through, and the MP startup order GPU → CPU → local SSD → shared storage → discovered peer CPU. The priority and generated-reply admission are configurable. Host and bounded native SSD pools poll once per second and reclaim 20% of resident entries at 80% usage. The MP server requires an explicit eviction policy. The simulator uses LRU as in the validated recipe. Its hard capacity limit approximates allocation pressure between polls. S3 estimates include PUT, GET and metadata HEAD operations, grouped by rank and billed outside warm-up.

The replay checks cache state at prefill service start. Prompt KV becomes readable in GPU and CPU memory after prefill, and on each backing tier after its modeled asynchronous write. Optional reply chunks are eligible after response completion. Concurrent reads and writes share a FIFO payload lane on each private SSD. Peer transfers occupy both nodes’ network interfaces. Object storage and prefill-to-decode transfers use the prefill node’s interface. The model treats metadata probes for one request as parallel and adds one S3 round trip when any HEAD is needed. These timing choices approximate a deployment.

Decode admits ready sequences at step boundaries and checks peak active KV separately from the reusable GPU cache budget. Synthetic follow-ups start their think time after the last reply token. Imported traces preserve the recorded arrivals. Billing attributes storage writes and operations to the requests admitted during the measurement window, including their outstanding work. Stored-byte SSD pricing applies retention and capacity limits independently to each node.

For DeepSeek V4.1 Flash on B200, each of three ratio-2 owners and one ratio-1 owner stores a 528-byte compressed KV record and 132-byte index record. This averages 1,650 bytes per input token for one KV copy. Forty sliding-window layers also keep up to 128 rows each, totaling 2,703,360 live bytes. Hopper uses a 584-byte KV row. With the pinned vLLM default of bounded replay, the GPU, CPU, SSD and S3 prefix caches retain only the global KV and index records. The replay charges compute for up to 128 trailing tokens on a hit. Active requests need live window memory, and a disaggregated handoff transfers the live state. [vLLM bounded replay default](https://github.com/vllm-project/vllm/blob/82c6b325b49ce361f5a295eb7d932e1b439e187d/vllm/config/cache.py) · [Sliding-window cache policy](https://github.com/vllm-project/vllm/blob/82c6b325b49ce361f5a295eb7d932e1b439e187d/vllm/v1/core/single_type_kv_cache_manager.py)

The replay counts GPU TP replicas and models one external MLA copy per pipeline stage under the v0.5.7 connector. Its GPU chart uses the replay chunk granularity. [Release parallel strategy](https://github.com/LMCache/LMCache/blob/v0.5.7/lmcache/integration/vllm/vllm_multi_process_adapter.py)

The chart counts payload bytes. Paging alignment, allocator slack, locked objects, asynchronous write completion, HTTP retries and multipart transfers require runtime measurements. [LMCache recipe](https://docs.lmcache.ai/recipes/deepseek_v41_flash.html) · [vLLM attention implementation](https://github.com/vllm-project/vllm/blob/82c6b325b49ce361f5a295eb7d932e1b439e187d/vllm/models/deepseek_v41/attention.py) · [AWS pricing](https://aws.amazon.com/s3/pricing/)

## Historical audit before the simulator update

The comparisons, numerical examples and proposed changes below describe the previous simulator.

**November 19, 2026.** Local GPU, local CPU, local SSD, peer CPU and S3 can participate in one vLLM + LMCache multiprocess (MP) deployment. The web simulator’s fixed choice of **SSD → peer → S3** on a local memory miss is a custom read policy. With SSD and S3 configured at startup and peers discovered normally, the stock MP policy prefers **SSD → S3 → peer** when more than one holds the needed object. The simulator is suitable for comparing hypothetical deployments. Its first-S3-read minute, TTFT and dollar figures need calibration before use as LMCache deployment predictions.

## What is configurable

| Simulator control or behavior | LMCache counterpart and consequence |
| --- | --- |
| GPU KV budget, model, GPUs per node, nodes | vLLM owns GPU blocks, parallelism and GPU memory allocation. The simulator estimates usable memory after weights and runtime reserves, then applies a workload fraction. LMCache’s L1 size controls host storage. Per-instance GPU capacity should be checked against vLLM’s reported block/token capacity for the chosen layout. [Model recipe](https://docs.lmcache.ai/recipes/deepseek_v41_flash.html) |
| CPU capacity per node | A local MP server can size its DRAM L1 with `--l1-size-gb`. This maps to a per-node value when each node runs one such server. The replay pools CPU and SSD capacity across all pipeline stages in a group. Real storage follows server placement and rank ownership. A simulator setting of zero CPU with SSD/S3 still active also omits the L1 buffers MP needs for staging. Buffer-only L1 is available via the store/prefetch policies. [MP configuration](https://docs.lmcache.ai/mp/configuration.html) |
| Local SSD size and S3 together | Repeat `--l2-adapter`. For a bounded directory-backed cache, use `fs_native` with both `max_capacity_gb` and an `eviction` policy. The size alone enables accounting. Plain MP `fs` exposes no aggregate capacity signal for the watermark controller. S3 is a separate adapter with its own endpoint and region. S3 Express requires a suitable bucket and signing configuration. The simulator’s Gen4/Gen5 choice supplies bandwidth and pricing assumptions. [Native filesystem implementation](https://github.com/LMCache/LMCache/blob/v0.5.7/lmcache/v1/distributed/l2_adapters/fs_native_l2_adapter.py) · [Plain filesystem implementation](https://github.com/LMCache/LMCache/blob/v0.5.7/lmcache/v1/distributed/l2_adapters/fs_l2_adapter.py) · [S3 adapter](https://github.com/LMCache/LMCache/blob/v0.5.7/docs/source/mp/l2_storage/s3.rst) |
| Peer CPU cache and interconnect | Symmetric P2P reads another server’s L1. Peer capacity is already counted on its owner, as on our chart. It requires peer discovery, routable endpoints and a working transfer engine. Adding a node or choosing a nominal link speed in the simulator enables P2P automatically when another cache group is available. Actual link throughput, discovery, locking, timeouts and staging determine real hits and latency. Current development also documents a separate headless-peer **write** mode triggered by local L1 usage. The simulator models symmetric reads. [Release P2P setup](https://github.com/LMCache/LMCache/blob/v0.5.7/docs/source/mp/p2p.rst) · [Development P2P deployment modes](https://github.com/LMCache/LMCache/blob/c7e1e1f4cedac99c4fa9e7beefd94b8b2a5b2650/docs/source/mp/p2p_deployment.rst) |
| Exact fetch order | The stock planner assigns each eligible object to local L1 first, then the lowest-indexed L2 that has it. Startup adapters get successive IDs. Discovered peers get IDs later. The controller can issue lookup-and-lock operations to multiple adapters before it picks the data source, so an S3 probe and an S3 data read are distinct. A custom registered prefetch policy can prefer peer adapters over S3 regardless of discovery order. The older in-process connector has different configuration. In v0.5.7 its `retrieve_locations` filters the registered backends by membership and does not reorder them. [MP planner](https://github.com/LMCache/LMCache/blob/v0.5.7/lmcache/v1/distributed/storage_controllers/prefetch_policy.py) · [ID allocation](https://github.com/LMCache/LMCache/blob/v0.5.7/lmcache/v1/distributed/storage_manager.py) · [Peer registration](https://github.com/LMCache/LMCache/blob/v0.5.7/lmcache/v1/multiprocess/modules/p2p_controller.py) · [Policy extensions](https://github.com/LMCache/LMCache/blob/v0.5.7/docs/source/mp/l2_storage/index.rst) · [In-process manager](https://github.com/LMCache/LMCache/blob/v0.5.7/lmcache/inprocess/v1/storage_backend/storage_manager.py) |

**Example configuration.** Start one coordinator, then a server per inference node. These are connection and storage settings for a compatible installation with the native FS, S3 and P2P dependencies, a node-local mounted SSD and access to a common bucket. Substitute the actual addresses, bucket and region. Configure each vLLM replica to use its local server through `LMCacheMPConnector` with `kv_role=kv_both` and prefix caching. The example uses stock adapter priority. [Release deployment flags](https://github.com/LMCache/LMCache/blob/v0.5.7/docs/source/mp/p2p.rst) · [L2 adapter configuration](https://github.com/LMCache/LMCache/blob/v0.5.7/docs/source/mp/configuration.rst)

```bash
# Once
lmcache coordinator --host 0.0.0.0 --port 9300

# On each inference node, with NODE_IP set to its own routable address
lmcache server --host 0.0.0.0 --port 5555 --http-port 8080 \
  --chunk-size 256 --l1-size-gb 4 --eviction-policy LRU --l1-align-bytes 65536 \
  --coordinator-url "http://${COORDINATOR_IP}:9300" \
  --coordinator-advertise-ip "${NODE_IP}" --p2p-advertise-url "${NODE_IP}:8500" \
  --l2-adapter '{"type":"fs_native","base_path":"/mnt/local-ssd/lmcache","max_capacity_gb":8,"eviction":{"eviction_policy":"LRU","trigger_watermark":0.8,"eviction_ratio":0.2}}' \
  --l2-adapter '{"type":"s3","s3_endpoint":"s3://example-bucket","s3_region":"us-west-2"}'
```

| Write timing and visibility | All complete cache blocks become visible to the next arrival immediately, including replies that would still be generating. Writes consume no bandwidth or queue time. | Eager offload is the default. GPU→L1 transfer and subsequent L2 stores have separate completion events. A follow-up on another node can arrive before a copy is readable. Optional eviction-aware lazy offload moves the GPU→L1 store closer to GPU eviction. L2 placement is a separate decision. The main replay uses a minimum of 512 tokens per block and synthetic prefix IDs. | MP defaults to saving prompt chunks, with `lmcache.mp.save_decode_cache=false`. Reply tokens can be written later when they reappear in a prompt. The default minimum chunk size is 256, negotiated to a compatible model geometry. Complete chunks are the usual default. Actual keys include model, KV rank, chunk identity and cache salt. A bandwidth preset cannot calibrate contention or TTFT under load. The chart’s tier TTFT is the whole-request mean of readers, so one request can appear in multiple rows. ## Does NVL72 change which GPU serves a prefix?

A GB200 NVL72 rack connects 72 GPUs across 18 four-GPU compute trays. A follow-up routed to the same inference replica can reuse its resident GPU KV, including the portions held by ranks of that replica. A follow-up routed to a different replica has a different local GPU cache. Stock LMCache MP P2P exposes peer servers’ registered L1 buffers (normally host DRAM). NVLink connectivity alone gives the other replica’s GPU memory no lookup priority. Routing the request to the replica that owns the prefix can produce a GPU hit without transferring that prefix between replicas. [NVIDIA rack topology](https://docs.nvidia.com/base-command-manager/product-manuals/nvidia-mission-control/nvlinkinfo) · [LMCache P2P lookup and transfer](https://docs.lmcache.ai/mp/p2p.html)

The simulator assigns a request to a prefill replica before lookup and checks only that replica’s GPU cache. The GB200 preset specifies a 72-GPU NVLink domain for modeling expert-parallel decode communication. It does not introduce a peer-HBM read path or automatically select a full rack. Consequently the GPU hit rate and TTFT charts cannot estimate a deployment that explicitly fetches reusable blocks from another replica’s HBM. ## Controlled replay

The disk-pressure example uses DeepSeek V4.1 Flash, two nodes with eight B200s each, 600 requests/minute, 80% follow-ups, five-minute mean think time, 1% GPU KV budget, 4 GiB host RAM and 8 GiB SSD per node, and S3 Standard. The simulation ran from cold for an hour with its fixed seeds. In a temporary copy I swapped only the peer and shared entries in the lower-tier lookup array. The same requests, cache writes, capacities, network timing and prices were used in each pair.

| Request routing | Priority after local SSD | Mean TTFT | First S3 data read | Prompt tokens from peer | Prompt tokens from S3 |
| --- | --- | ---: | ---: | ---: | ---: |
| Sticky | Peer first (current UI) | 101.15 ms | min 48 | 0.0024% | 0.1748% |
| Sticky | S3 first (stock startup order) | 101.15 ms | min 1 | 0% | 0.1772% |
| Random | Peer first (current UI) | 125.07 ms | min 21 | 6.3109% | 3.5714% |
| Random | S3 first (stock startup order) | 181.49 ms | min 1 | 0% | 9.8823% |

Sticky routing illustrates why **first read** and **impact on typical latency** are different metrics. A shared system prefix can be read on a different replica in minute one, long before its local SSD fills. Random routing makes the priority decision frequent enough to add 56.42 ms to the replay mean. All four runs priced the backing tiers at $0.002246/h because this S3 Standard preset has no per-read charge in the model.

As a separate check, I kept S3-first priority and limited external writes to complete prompt blocks while keeping the original GPU insertions. S3 occupancy at minute 60 fell from **26.06 to 23.24 GiB**, and estimated backing cost fell to **$0.002157/h**. This isolates one default that affects the chart even when the lookup order is correct. All values in this section are simulator outputs.

## What would validate a production estimate

The first changes for an LMCache-specific simulation are an explicit prefetch policy, separate GPU and external chunk admission, and measured per-group sizes for the selected model. Then replay the same tokenized chats and routing on a matched vLLM/LMCache topology. Record GPU block capacity, resident L1/L2 bytes, per-adapter completed loads and stores, S3 operation counts and client-observed TTFT. A decisive priority test is a prefix absent from local GPU, CPU and SSD but present on both a peer and S3. Correlate the completed adapter load with the request trace. Run that case under each policy before interpreting the occupancy threshold as the cause of a TTFT change.
