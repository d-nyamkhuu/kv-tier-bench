# Controls for a tiered KV cache simulator

The question for this interface is what happens when a conversation returns after other requests have used the fast cache. A useful experiment varies traffic or capacity, then observes which tier supplies the prefix, how long the request queues, and what the backing store costs.

| Related tool | What the user supplies | What the tool checks |
| --- | --- | --- |
| [Mooncake KV Cache Hit Rate Simulator](https://kvcache.ai/tools/kv-cache-hit-rate-simulator/) | A trace or uploaded prefix hashes, block size, model, KV precision, memory budget, and eviction policy | Prefix hit rate and ideal prefill speedup across cache budgets. Comparison policies include FIFO, LRU, and optimal eviction. |
| [KVC-TierSim](https://github.com/sbu-fsl/KVC-TierSim) | GPU, DRAM, disk and link or a stack preset, model, block count, hit ratio, arrival rate, P95 target, and automatic or manual residency | Per-tier residency, restore and recompute rates, latency and whether a policy meets the target. This supports experiments where the hit ratio is already known. |
| [Microsoft Vidur](https://github.com/microsoft/vidur#running-the-simulator) | Request rate and arrival process, request-length trace, model, replicas, device, parallelism, and scheduling limits | TTFT and its tail, inter-token latency, batch size, and deployment capacity per dollar. This makes queueing and request lengths relevant when interpreting TTFT. |
| [GuideLLM multiturn benchmark](https://vllm-project.github.io/guidellm/latest/guides/multiturn/) | Turns per conversation, prompt and reply lengths, optional first-turn lengths, number and size of shared prefixes | Exercises a serving endpoint with growing histories, including long opening prompts and shorter follow-ups. It is a workload benchmark. |

## Design decisions

- **Visible by default.** Request rate determines how many arrivals compete for service and cache space. Follow-up share determines how often histories are reused. Time between turns determines how many other requests can arrive before that reuse. CPU capacity and backing-tier choice let users act on the resulting pressure.
- **One disclosure away.** Shared-prefix, message, and reply lengths change the bytes written per conversation and the work needed on a miss. GPU KV budget limits the share of usable KV memory available to this workload. These controls allow independent experiments on a fixed deployment.
- **Measured from each replay.** The first GPU eviction marks the onset of fast-tier pressure. The share of prompt tokens read from each tier measures the consequence. A first eviction may precede the first request that needs an evicted block. Queue time helps explain TTFT increases caused by saturation. The hourly cost covers backing storage, byte-transfer fees and estimated S3 requests.
- **Model limits.** The simple replay uses one shared system prefix, a fixed random seed, round-robin, sticky or random routing, and write-through LRU. Burst patterns, prefix-popularity distributions, demand-contended tier bandwidth, and alternative eviction policies can produce different results. A hit ratio supplied by the user would hide the effect this page is intended to reveal.
